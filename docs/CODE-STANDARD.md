# มาตรฐานคอมเมนต์ของโครงการ

เอกสารนี้กำหนดรูปแบบคอมเมนต์ที่ทุกไฟล์ซอร์สในโครงการต้องมี
เพื่อให้เปิดไฟล์ขึ้นมาแล้ว **รู้ทันทีว่าไฟล์นี้คืออะไร เวอร์ชันอะไร และมีอะไรเพิ่มเข้ามาบ้าง**
โดยไม่ต้องไปไล่อ่าน git log หรือ CHANGELOG

รูปแบบที่ใช้คือ **Doxygen** ซึ่งเป็นมาตรฐานที่ใช้กันทั่วไปในงานเฟิร์มแวร์
แท็กทุกตัวที่ใช้ในเอกสารนี้เป็นแท็กจริงของ Doxygen ไม่ได้คิดขึ้นเอง
ถ้าวันหนึ่งอยากสร้างเอกสารอัตโนมัติจากโค้ด ก็รัน Doxygen ได้เลยโดยไม่ต้องแก้อะไร

---

## 1. หัวไฟล์ (บังคับทุกไฟล์)

ทุกไฟล์ `.ino` และ `.h` ต้องขึ้นต้นด้วยบล็อกนี้

```c
/**
 * @file      ชื่อไฟล์.h
 * @brief     ไฟล์นี้ทำอะไร หนึ่งบรรทัด
 * @version   113.1.0
 * @date      2026-09-22
 * @author    Kittiphan Rattanakorn <varitwuttikul@gmail.com>
 *
 * @par Organization
 * มหาวิทยาลัยมหาจุฬาลงกรณราชวิทยาลัย วิทยาเขตแพร่
 *
 * @par Description
 * คำอธิบายยาวได้ตามต้องการ ว่าไฟล์นี้รับผิดชอบส่วนไหนของระบบ
 *
 * @par Revision History
 * | Version | Date | Change |
 * |---|---|---|
 * | 113.1.0 | 2026-09-22 | สิ่งที่เปลี่ยนในเวอร์ชันนี้ |
 * | 113.0.0 | 2026-09-22 | สิ่งที่เปลี่ยนในเวอร์ชันก่อน |
 *
 * @warning  เรื่องที่ถ้าไม่รู้แล้วจะพัง
 * @note     เรื่องที่ควรรู้แต่ไม่ถึงกับพัง
 */
```

### กติกาของแต่ละแท็ก

| แท็ก | บังคับ | กติกา |
|---|---|---|
| `@file` | ✅ | ต้องตรงกับชื่อไฟล์จริง |
| `@brief` | ✅ | หนึ่งบรรทัด ไม่เกินหนึ่งประโยค |
| `@version` | ✅ | ไฟล์ `.ino` ต้องตรงกับ `APP_VERSION` **เป๊ะ** · ไฟล์ `.h` คือ **เวอร์ชันที่ไฟล์นี้ถูกแก้ครั้งล่าสุด** ต้องเป็นแถวบนสุดของตารางของตัวเอง และต้องไม่ใหม่กว่า `APP_VERSION` |
| `@date` | ✅ | รูปแบบ `YYYY-MM-DD` เท่านั้น คือวันที่แก้ไขล่าสุด |
| `@author` | ✅ | ชื่อผู้พัฒนาหลัก |
| `@par Revision History` | ✅ | ตารางเรียงจาก**ใหม่ไปเก่า** แถวบนสุดต้องตรงกับ `@version` ของไฟล์ · ใส่เฉพาะเวอร์ชันที่ไฟล์นี้**ถูกแก้จริง** ไม่ต้องใส่เวอร์ชันที่ไม่ได้แตะไฟล์นี้ |
| `@warning` / `@note` | ตามสมควร | ใส่เมื่อมีเรื่องที่คนมารับช่วงต่อต้องรู้ |

> ทั้งหมดนี้ถูกตรวจอัตโนมัติด้วย `python3 tools/proto-check/headercheck.py`
> ถ้าลืมอัปเดตเลขเวอร์ชันหรือลืมเติมแถวใหม่ในตาราง ตัวตรวจจะฟ้อง
>
> **ตัวอย่างจริง** `HostScreen.h` ค้างอยู่ที่ `113.0.0` ขณะที่สเก็ตช์เป็น `113.1.0`
> เพราะรุ่น 113.1.0 แก้แค่หน้าเว็บ ไม่ได้แตะไฟล์วาดจอเลย **นี่คือสิ่งที่ถูกต้อง**
> การไล่ขยับเลขทุกไฟล์ให้เท่ากันหมดจะทำให้ตารางโกหกว่าไฟล์นั้นถูกแก้ทั้งที่ไม่ได้แก้

## 2. ป้ายบอกเวอร์ชันในโค้ด

หัวไฟล์บอกภาพรวม แต่ไม่ได้บอกว่า **บรรทัดไหน** เพิ่มมาตอนไหน
เวลาเพิ่มหรือแก้อะไรที่ไม่ใช่เรื่องเล็ก ให้ปักป้ายไว้เหนือจุดนั้น

```c
// [113.0.0] เพิ่ม: ข้อมูลสดสำหรับแดชบอร์ด หน้าเว็บดึงชุดนี้ทุกสองวินาที
void handleDashboardAPI() {
```

รูปแบบคือ `// [เลขเวอร์ชัน] คำกริยา: คำอธิบาย` โดยคำกริยาใช้สามคำนี้เท่านั้น

| คำกริยา | ใช้เมื่อ |
|---|---|
| **เพิ่ม** | ของใหม่ที่ไม่เคยมีมาก่อน |
| **แก้** | ของเดิมที่ทำงานผิดแล้วซ่อม |
| **ย้าย** | ของเดิมที่ย้ายที่อยู่ ตรรกะไม่เปลี่ยน |

เลขเวอร์ชันในป้ายต้องมีอยู่จริงในตาราง Revision History ของไฟล์นั้น
ตัวตรวจจะฟ้องถ้าปักป้ายด้วยเลขที่ไม่มีในตาราง

**ไม่ต้องปักป้ายกับ** การแก้คำผิด จัดย่อหน้า เปลี่ยนชื่อตัวแปร
หรือการแก้เล็ก ๆ ที่อ่านโค้ดแล้วเข้าใจได้เอง ป้ายที่เยอะเกินไปจะกลายเป็นขยะ

## 3. คอมเมนต์ในเนื้อโค้ด

- **เขียนเป็นภาษาไทย** เพราะคนที่มารับช่วงดูแลต่อคือนิสิตของวิทยาเขต
  ส่วนข้อความที่ผู้ใช้เห็นบนจอและบนหน้าเว็บเป็นภาษาอังกฤษ คนละเรื่องกัน
- **อธิบายว่าทำไม ไม่ใช่ทำอะไร** โค้ดบอกอยู่แล้วว่าทำอะไร
  สิ่งที่โค้ดบอกไม่ได้คือเหตุผล เช่น *"แยกบัสจอออกจากเครื่องอ่านบัตร
  เพราะไลบรารี MFRC522 ยึดตัวแปร SPI มาตรฐานไว้ ถ้าใช้ร่วมกันจอจะเพี้ยนหลัง PCD_Init()"*
- **ห้ามเขียนคอมเมนต์รับประกันสิ่งที่ยังไม่ได้ทดสอบ** เคยเกิดขึ้นมาแล้วว่า
  มีคอมเมนต์เขียนไว้ว่า *"การใส่เพิ่มเฉย ๆ ปลอดภัย"* ทั้งที่ไม่เคยลองจริง
  แล้วทำให้ชื่อ Wi-Fi ไม่ขึ้นมาให้เลือก ถ้ายังไม่ได้ทดสอบให้เขียนตรง ๆ ว่ายังไม่ได้ทดสอบ

## 4. ตรวจก่อน commit ทุกครั้ง

```sh
python3 tools/proto-check/headercheck.py   # หัวไฟล์และป้ายเวอร์ชัน
python3 tools/proto-check/bracecheck.py    # วงเล็บและเครื่องหมายคำพูด
python3 tools/proto-check/splitcheck.py    # ปัญหาจากการแยกโค้ดไปไว้ในไฟล์ .h
python3 tools/proto-check/protoscan.py Canteen_Host_Server/Canteen_Host_Server.ino \
                                       Canteen_Station_Client/Canteen_Station_Client.ino
```

ทั้งสี่ตัวไม่ได้แทนการคอมไพล์ เป็นแค่ตัวกันความผิดพลาดที่เคยเกิดขึ้นจริงมาแล้ว
**การคอมไพล์และทดสอบบนเครื่องจริงยังจำเป็นเสมอ**
